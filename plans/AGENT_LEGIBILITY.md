# Agent legibility — making AnyInfer correct to write *by* a coding agent

**Scope:** artifacts that let a coding agent working in *someone else's* repository write
correct AnyInfer code: a machine-readable docs index (`llms.txt`), a generated
instruction fragment (`anyinfer agents-md`), and a distributable skill/prompt pair for the
three agent tools this project already supports. **Goal:** the most common way this
library gets integrated in 2026 is "a coding agent writes the integration"; make that path
produce idiomatic, current code instead of plausible-looking API that never existed.
**Non-goal:** shipping an agent, a framework, or runtime prompts. Every artifact here is
static text derived from canonical sources.

**Audience for this plan:** contributors editing the existing files directly. Code audit
is as of **2026-08-09**; re-verify before starting each task.

**Authority:** AGENTS.md ("Instruction authority and workstreams" — one canonical
procedure, thin tool-specific entry points; "No ADR mentions in user-facing text");
DESIGN.md §25 (documentation plan).

**Governance intent:** no ADR. One policy addition to AGENTS.md is required: the
instruction-authority rule currently governs files *inside* this repository, and this
plan produces instruction text that ships *outward*. Extend the rule to say generated
consumer-facing agent instructions are derived from canonical sources and are covered by
the same shim tests. **The no-ADR-in-user-facing-text rule applies to every artifact
here** — these are the most likely place for `ADR-003` to leak into a stranger's repo.

---

## 1. Motivation and evidence

This repository already treats agent instructions as a governed surface, and has the
tests to prove it:

- [AGENTS.md](../AGENTS.md) is canonical; `CLAUDE.md` and
  `.github/copilot-instructions.md` are shims.
- [contracts/DRIFT-CHECK.md](../contracts/DRIFT-CHECK.md) is one canonical procedure with
  three thin entry points (`.agents/skills/`, `.claude/skills/`, `.github/prompts/`).
- [tests/test_agent_instructions.py](../tests/test_agent_instructions.py) enforces both:
  shims must defer, must say "only authoritative", and must stay under a word budget.

That discipline is pointed inward. Nothing is pointed outward, and the outward case is
where the failure is expensive: an agent integrating this library from pre-training and a
web search will confidently produce an OpenAI-clone call surface — `client.chat.completions`,
a `model=` kwarg, `response_format` — because that is what almost every other library in
this space looks like. AnyInfer is deliberately *not* that (ADR-001), so the most
predictable wrong answer is also the most likely one.

Concrete traps an agent will hit without guidance, all of them things this library does
differently on purpose:

| Trap | The actual API |
|---|---|
| `model="claude-sonnet-4-5"` | `target="anthropic:claude-sonnet-4-5"` — provider-qualified, split on the first colon |
| `response_format={"type": "json_object"}` | `schema=` on the request; the mechanism is chosen for you |
| Retry wrapped around the call | `Route` / `Retry` — the router owns it |
| Reading `result.usage.cost_usd` as a float | `Decimal`, and `None` means *unknown*, never zero |
| Treating a capability value as a plain number | `Sourced[T]` carries provenance |
| `pip install anyinfer[anthropic]` | there is no such extra; hosted adapters are core |

## 2. The three artifacts

### 2.1 `llms.txt` and `llms-full.txt` (docs site)

Generated at docs-build time by a new hook in
[scripts/mkdocs_hooks.py](../scripts/mkdocs_hooks.py) (which already exists and already
injects the release version, so the build-time generation pattern is established).

- `llms.txt` — the index: project summary, then a curated link list by task, following
  the community convention (H1, blockquote summary, `## Section` + `- [title](url): note`).
- `llms-full.txt` — concatenated body text of the guides and the API reference, with
  navigation chrome stripped.

Both are generated from `mkdocs.yml`'s `nav` and the built pages, so a new page appears
automatically and a deleted one cannot linger. Neither is hand-maintained.

### 2.2 `anyinfer agents-md` (CLI)

Emits a ready-to-paste instruction fragment for the *consuming* repository:

```
$ anyinfer agents-md >> AGENTS.md
$ anyinfer agents-md --format claude > CLAUDE.md
$ anyinfer agents-md --config anyinfer.json     # tailored to what this app configured
```

Content is short (target ~60 lines) and is exactly the trap table above plus the
call-shape skeleton, rendered from **live introspection** rather than a frozen string:
the provider list comes from the registry, the extras list from installed distribution
metadata, and the version from the package. A fragment generated by version 0.3 says
what 0.3 actually offers.

With `--config`, it additionally names the configured providers and default route, so the
agent working in that repo writes targets that exist there.

### 2.3 A distributable skill

`anyinfer-integration` — one canonical procedure file plus thin entry points, mirroring
the drift-check structure exactly: `contracts/`-style canonical text lives at
`docs/agents/INTEGRATION.md`; the Codex skill, Claude skill, and Copilot prompt are
shims that point at it. Published in-repo (usable by contributors) and documented for
consumers to copy into their own `.claude/skills/` or `.agents/skills/`.

## 3. Design constraints

1. **Derived, never authored twice.** Every artifact is generated or is a shim. A
   hand-written second description of the API is a guarantee of drift — this is the same
   argument AGENTS.md already makes for tool-specific instruction files.
2. **No ADR identifiers, anywhere.** These are user-facing. State rules in plain words:
   "adapters only translate; retry and validation live in the core" — not "ADR-003".
3. **Version-stamped.** Every generated artifact carries the version it was generated
   from. An agent reading a stale fragment should be able to notice.
4. **No prompts at runtime.** Nothing here is loaded, sent, or interpolated by the
   library at request time. These are files.

## 4. Tasks

**AL.1 — `llms.txt` generation.** Extend [scripts/mkdocs_hooks.py](../scripts/mkdocs_hooks.py)
with `on_post_build` writing both files into the site root; add them to
`mkdocs.yml`'s `not_in_nav` handling if needed. *Acceptance:* `mkdocs build` produces
both; a new nav entry appears in `llms.txt` without any hand edit; a test asserts the
files exist and that `llms.txt` contains no `ADR-` token.

**AL.2 — `anyinfer agents-md`.** New `_agents_md` in [cli.py](../src/anyinfer/cli.py) with
`--format {agents,claude,copilot}` and `--config`. Template lives in a data module, not
inline. *Acceptance:* `tests/test_cli_agents_md.py` asserts: output names only registered
providers; output names only real extras (cross-checked against
[pyproject.toml](../pyproject.toml) `optional-dependencies`); output contains no `ADR-`;
`--config` output names the configured targets.

**AL.3 — the trap table is executable.** Every "actual API" cell in §1 is backed by a
runnable snippet in the docs-examples suite, so a wrong claim fails CI rather than
misleading an agent. *Acceptance:* `tests/test_docs_examples.py` covers each row.

**AL.4 — `docs/agents/INTEGRATION.md` + three shims.** Canonical procedure: how to
integrate, what to check (`anyinfer verify`), what never to hand-roll (retry, schema
validation, provider branches). Shims at `.agents/skills/anyinfer-integration/SKILL.md`,
`.claude/skills/anyinfer-integration/SKILL.md`,
`.github/prompts/anyinfer-integration.prompt.md`. *Acceptance:* extend
[tests/test_agent_instructions.py](../tests/test_agent_instructions.py) with the same
three assertions it already makes for the drift-check trio — defers to the canonical
file, says "only authoritative", stays under the word budget.

**AL.5 — AGENTS.md policy amendment.** One paragraph extending instruction authority to
outward-facing generated instructions. *Acceptance:* the existing
`test_agents_file_owns_every_workstream` still passes; a new assertion covers the added
rule.

**AL.6 — docs page.** `docs/guides/coding-agents.md` (nav: Integrate): what the artifacts
are, how to install the skill into a consuming repo, and the honest caveat that a
generated fragment reflects the installed version. Link from the README's role-based quick
links.

## 5. Testing

`tests/test_cli_agents_md.py`, additions to `tests/test_agent_instructions.py` and
`tests/test_docs_examples.py`, plus one docs-build assertion for the `llms.txt` hook. The
`ADR-` leak check should be a single shared helper applied to every generated artifact and
every file under `docs/` — the rule already exists in AGENTS.md but is not currently
enforced by a test, and generation makes enforcement cheap.

## 6. Risks

- **R-AL1 — instruction drift into fiction.** A generated fragment that describes an API
  version the agent is not using is worse than none. Mitigate: version stamp, registry
  introspection rather than frozen lists, CI-executed snippets.
- **R-AL2 — perceived gimmick.** "AI-friendly docs" reads as marketing unless the content
  is genuinely the trap list. Mitigate: keep the fragment short and adversarial — it
  exists to correct predictable wrong guesses, not to advertise.
- **R-AL3 — maintenance surface.** Three more shim files to keep honest. Mitigate: they
  are covered by the same test that already polices the drift-check trio.

## 7. Decisions (2026-08-09)

1. **Repo-only skill, no `--install`, no package data.** The canonical file and its three
   shims live in this repository and are copied by users who want them. The library never
   writes into someone's `.claude/`, `.agents/`, or `.github/` directory, and the wheel
   carries no skill payload. `anyinfer agents-md` still prints to stdout, so
   `anyinfer agents-md >> AGENTS.md` remains the one-liner — the user's own redirect is
   the confirmation step. `AL.2` therefore ships no `--install` flag and no file-writing
   path at all.
2. **`llms-full.txt` splits if it gets large.** One file while the built docs stay under
   roughly 200k tokens; beyond that, a per-section split with `llms.txt` as the index.
   `AL.1` should log the generated size at build time so the threshold is observed rather
   than guessed at.
